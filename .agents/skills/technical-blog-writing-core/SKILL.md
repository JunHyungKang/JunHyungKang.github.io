# Technical Blog Writing Core

개발자 독자를 위한 기술 블로그 작성·리라이트 절차를 제공한다.
특정 외부 CLI나 SaaS 명령에 의존하지 않고, 구조·근거·재현성을 우선한다.

## 목표

다음 기준을 만족하도록 작성한다.

- 문제와 해결을 빠르게 이해 가능
- 작성자가 직접 구현·검증한 기여를 명확히 식별 가능
- 코드 예제를 실제로 재현 가능
- 주장의 강도와 수치·근거의 강도 일치
- 트레이드오프와 한계 명시

## 글 유형 선택

요청 의도에 맞는 유형을 먼저 선택한다.

1. Tutorial / How-to: 단계별 구현 안내
2. Deep Dive / Explainer: 개념·원리·내부 동작 설명
3. Postmortem / Incident: 장애 원인·대응·재발 방지
4. Benchmark / Comparison: 방법론 기반 비교와 해석
5. Architecture / System Design: 선택 근거와 트레이드오프

## 기본 작성 절차

1. 독자와 전제 정의
   - 대상 독자(입문/중급/고급) 명시
   - 사전 지식, 런타임/프레임워크 버전 명시
2. 기여 범위와 근거 분리
   - 공개·재사용 기준선과 작성자가 직접 구현·검증한 작업 분리
   - 핵심 주장마다 수치, 로그, 코드, 실험 또는 재현 절차 연결
3. 문제 정의
   - 핵심 문제를 1~2문장으로 제시
   - 왜 중요한지 수치/실패 사례로 연결
4. 아웃라인 구성
   - 문제 → 기준선과 기여 범위 → 접근 → 구현/검증 → 결과 → 한계 → 결론
5. 본문 작성
   - 섹션마다 주장 → 근거 → 예시 순서 유지
6. 최종 검증
   - 체크리스트로 소유권·구조·근거·재현성 점검

## 기술적 신뢰도 게이트

공개 기술 글을 경력 신호로 검토한다.

1. **기여 범위를 먼저 고정한다.**
   - 전체 결과, 공개·재사용 기준선, 작성자가 직접 만든 변화와 검증을 구분한다.
   - 에이전트가 수행한 작업과 작성자가 설계·판단·검증한 작업도 필요한 경우 구분한다.
2. **제목과 도입부에 가장 강한 증거를 배치한다.**
   - 직접 만든 결과, 구체적인 실패, 바뀐 기술적 판단을 먼저 보여준다.
   - 토큰 수, 실행 시간, 순위처럼 큰 숫자가 직접 기여를 가리면 제목이나 첫 화면에서 내린다.
3. **주장의 강도를 증거에 맞춘다.**
   - 통제된 비교가 있으면 인과적 주장을 검토한다.
   - 통제된 비교가 없으면 운영상 관찰 또는 가설로 표현하고, 무엇을 증명하지 못했는지 밝힌다.
4. **재현 가능한 증거를 최소 하나 포함한다.**
   - 코드, 설정, 실험 표, 로그, 입력·출력 예시, 정확한 검증 절차 중 하나를 연결한다.
5. **실패 회고를 일반론으로 끝내지 않는다.**
   - 가설 → 실행 → 실패 신호 → 변경한 게이트 → 남은 한계 순서로 설명한다.

## 권장 본문 구조

```markdown
# 제목 (결과/효과가 드러나게)

**TL;DR:** 핵심 요약 2~3문장

## 문제 정의
- 현재 상태, 병목, 실패 맥락

## 기준선과 기여 범위
- 공개·재사용한 입력
- 직접 구현·검증한 변화

## 접근 방법
- 선택한 방법과 선택 이유

## 구현
- 단계별 설명 + 코드 + 실행 결과

## 결과
- 측정 수치, 비교 표/그래프, 관찰

## 트레이드오프와 한계
- 적용이 불리한 조건, 운영 비용

## 결론
- 적용 기준, 다음 액션

## 참고 자료
- 공식 문서, 벤치마크, 관련 글
```

## 개발자 글쓰기 규칙

### 톤

- 단정적으로 쓰되 과장하지 않기
- 마케팅 표현보다 기술 근거 우선
- 대안과 한계를 숨기지 않기

### 권장 표현

- "p99 지연시간 820ms→95ms 감소"
- "복잡도는 증가하지만 콜드스타트 비용은 감소"
- "Node 20.11 / React 19 기준 검증"

### 금지 표현

- "요즘 빠르게 변화하는 시대에"
- "그냥/쉽게/simply"
- "당연히/obviously"
- 근거 없는 "혁신적", "압도적"

### 한국어 전문가 문체 게이트

- 릴리스 노트나 공식 문서의 목차를 그대로 번역해 다시 쓰지 않는다. 작성자가 실제로 멈춰 본 코드, 실패한 import, 바뀐 판단 중 하나로 시작한다.
- 한국어가 더 분명하면 `action`, `production`, `exact pin`, `revision` 같은 번역투 영어를 쓰지 않는다. API 이름과 코드 식별자는 그대로 둔다.
- 모든 글을 `요약 표 → 번호 섹션 → exhaustive checklist`로 만들지 않는다. 표와 목록은 비교가 문장보다 빨리 읽힐 때만 쓴다.
- 짧은 판단문과 긴 설명문을 섞는다. 모든 문장을 같은 길이와 같은 종결어미로 정리하지 않는다.
- 유명 개발자의 팔로워 규모나 단정적인 어조를 흉내 내지 않는다. 직접 확인한 사실, 그 사실이 바꾼 판단, 아직 확인하지 못한 범위를 가져온다.
- 한국어 공개 글은 최종 편집 단계에서 `humanizer`로 AI 문체 패턴을 확인한다.

## 코드 예시 규칙

모든 코드 블록은 재현성을 기준으로 작성한다.

- 언어 식별자 포함 (```ts, ```py)
- 실행 전제(버전/의존성) 명시
- 복붙 실행 가능한 최소 완결 예시 우선
- 예상 출력/결과 함께 제시
- 실패 케이스 또는 에러 처리 최소 1개 포함

## 결과 섹션 규칙

가능하면 정량 수치를 포함한다.

- 전체 결과와 직접 기여 결과 분리
- Before/After
- 측정 조건(데이터 크기, 횟수, 런타임)
- 평균뿐 아니라 p95/p99 같은 tail 지표

수치가 없다면 관찰 근거를 명시한다.

- 로그 캡처
- 재현 절차
- 사용자 영향 범위

## 트레이드오프 필수 규칙

모든 기술 선택의 비용을 명시한다.

- 도입 복잡도
- 운영/디버깅 난이도
- 런타임/벤더 종속성
- 성능과 생산성의 균형

## 배포용 요약과 반응 평가

기술 전문가 게시물에서 반복되는 구조만 일반화해 적용한다. 유명인의 팔로워 규모, 글 길이, 단정적인 어조를 그대로 모방하지 않는다.

1. **한 게시물에 한 가지 역할만 부여한다.**
   - 직접 만든 결과를 보여주는 `build note`
   - 기술적 관찰 하나를 설명하는 `technical note`
   - 오류와 수정 내용을 공개하는 `correction`
   - 다음 탐색 방향을 묻는 `question or poll`
2. **첫 두 줄에서 행동과 의미를 밝힌다.**
   - `만들었다`, `측정했다`, `비교했다`, `틀렸고 고쳤다` 중 실제로 한 일을 먼저 쓴다.
   - 해당 결과가 개발자에게 왜 중요한지 한 문장으로 연결한다.
3. **구체적인 근거 2~4개만 남긴다.**
   - 수치, 아키텍처 차이, 실패 신호, 검증 조건처럼 판단을 바꾼 정보를 고른다.
   - 코드, 기술 도식, 결과 표, 실행 화면 등 정보를 담은 시각 자료를 우선한다.
4. **불확실성을 정확히 표시한다.**
   - 확인한 사실, 해석, 추측, 아직 모르는 점을 구분한다.
   - 한계나 오류를 숨기지 말고, 수정 게시물도 독립적인 신뢰 신호로 다룬다.
5. **주요 행동 요청을 하나만 둔다.**
   - 자세한 근거를 읽게 할 링크 또는 짧게 답할 수 있는 좁은 질문 중 하나를 중심에 둔다.
   - 글감을 검증하는 단계라면 구체적인 선택지가 있는 질문이나 설문을 사용한다.
6. **글 전체를 다시 요약하지 않는다.**
   - 링크드인 글만 읽어도 하나의 통찰은 얻되, 전체 근거와 구현은 원문에서 확인하게 한다.
7. **플랫폼별 노출 알고리즘에 관한 주장은 현재 공식 정보나 실제 분석 화면으로 확인한다.**
8. **명시한 기간의 퍼널로 평가한다.**
   - 노출과 도달
   - 반응과 댓글
   - 링크 클릭
   - 프로필 조회와 팔로워 변화
9. 계정의 기존 게시물과 비교하고, 좋아요나 댓글만으로 독자의 감정이나 작성자의 평판을 추론하지 않는다.
10. 링크 클릭이 거의 없다면 독자가 연결된 글을 평가했다고 결론 내리지 않는다.

## 리라이트 절차

1. 구조 교정: 결론/핵심을 앞당기기
2. 문장 교정: 한 문장 한 주장 원칙 유지
3. 근거 교정: 근거 없는 형용사 제거
4. 재현성 교정: 버전/입출력/전제 누락 보완
5. 독자성 교정: 대상 독자 수준에 맞게 깊이 조정

## 출력 형식

요청이 "초안 작성"이면 다음 순서로 출력한다.

1. 제목 후보 3개
2. TL;DR
3. 섹션별 아웃라인
4. 본문 초안
5. 체크리스트 기준 자체 점검 메모

요청이 "리라이트"이면 다음 순서로 출력한다.

1. 문제점 요약(구조/근거/표현)
2. 개선된 본문
3. 변경 이유 요약

요청이 "배포용 요약"이면 다음 순서로 출력한다.

1. 실제 행동과 의미를 담은 첫 두 줄
2. 근거 2~4개를 포함한 짧은 본문
3. 확인한 사실과 불확실성
4. 하나의 링크 또는 좁고 답하기 쉬운 질문
5. 게시 후 확인할 퍼널 지표

## 최종 체크리스트

- [ ] 제목에서 결과가 드러나는가?
- [ ] TL;DR이 2~3문장으로 명확한가?
- [ ] 공개·재사용 기준선과 직접 기여가 구분되는가?
- [ ] 가장 큰 숫자가 직접 기여를 가리지 않는가?
- [ ] 코드 예제가 실제 실행 가능한가?
- [ ] 버전/전제가 명시되었는가?
- [ ] 측정 근거(수치/방법)가 있는가?
- [ ] 주장 강도가 실험 설계와 일치하는가?
- [ ] 트레이드오프/한계를 숨기지 않았는가?
- [ ] 과장 표현을 제거했는가?
- [ ] 배포용 게시물이 한 가지 역할과 주장에 집중하는가?
- [ ] 배포용 요약이 글 전체를 반복하지 않는가?
- [ ] 다음 액션(적용 기준/확장 포인트)이 있는가?

## 제약

- 특정 외부 CLI 설치/실행 절차를 전제로 하지 않는다.
- 특정 서비스 벤더 종속 명령 대신 일반 원칙을 사용한다.
- 기술 정확성과 독자 신뢰를 최우선으로 유지한다.
